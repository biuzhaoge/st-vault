# Architecture and storage

[简体中文](architecture.md) · **English**

ST-Vault supports one administrator across multiple clients. A React/Vite workbench connects to Fastify through REST and SSE; one container runs Node, PostgreSQL 18 and FFmpeg for screenshots. The runtime has no browser, GPU decoding components or automatic key extractor. Dependency versions are defined by [package-lock.json](../package-lock.json) and the [Dockerfile](../deploy/Dockerfile).

## Data flow and module boundaries

Storage, HLS alignment and media directory dates remain UTC. The server validates deployment `TZ` and exposes it through the session API, giving every client the same display timezone independently of language. The timeline extends to the end of the current local day. Navigation uses local midnight and noon slots, with `@date-fns/tz` handling DST. Media duration uses actual UTC elapsed time.

The archive resolves the first real instant of each date in the deployment zone and checks for overlapping playable fragments from all broadcasters. A cross-midnight fragment keeps both dates visible. The timeline compresses completed dates with no footage and displays up to seven visible days. Date markers, status, coverage, drag selection and seeking share the same reversible mapping. When a query crosses a long gap, the workbench samples the visible spans in one archive snapshot. Media paths and timestamps continue to use UTC.

```text
Site cookies → Account information / complete following list
Anonymous status and HLS → Shared per-broadcaster ingress → Browser live playback
                                                       → Original media → Units → Screenshots
Browser commands → HTTP → Archive worker → Library journal + PostgreSQL hot indexes
```

## Status, recording and networking

“Record all models” is a persistent recording default, not an aggregate of individual switches. One archive transaction updates the default and all non-archived models. Newly added or re-followed models inherit it; routine list refreshes and online transitions preserve individual choices. Archiving still stops recording. The policy recovers with the portable library journal and uses the existing synchronization channel. An absent policy defaults to off; previous batch-operation intent is not inferred.

Status is evidence with an observation time and finite lease, not an indefinitely valid boolean. Failed/UNKNOWN results neither immediately overwrite known status nor renew it. A different known state requires an additional anonymous observation; confirmation backdates the transition to the first valid candidate observation. Privacy revocation does not wait for history confirmation. Restart and lease expiry preserve unknown gaps rather than inventing offline or continuous online states. Implementation and failure tests are in [provider](../apps/server/src/provider) and [archive](../apps/server/src/archive).

Broadcast status uses the bound site's public `/api/front/models/list` in batches of up to 50 IDs. An observation requires an exact requested ID and consistent `status` and `isLive` fields. Missing rows, contradictory flags, and failed requests leave the status unconfirmed. Only pending requests are coalesced, and observations retain the existing lease rules.

History is paginated by increasing event ID. Occurrence and detection times are separate, so late confirmation does not disturb read cursors. Opening History shows the latest entry and keeps it in view as entries arrive or the layout changes. Scrolling up preserves the reading position. Program events record normal shutdowns and abnormal shutdowns discovered on restart. The last heartbeat is only a lower bound on failure time. Events, status and read positions belong to the recoverable media library; the UI no longer draws orange downtime coverage blocks.

Each broadcaster shares one normal upstream production path. Live playback consumes buffered media while recording commits independently in order; it does not wait for disk publication. Recording preserves the highest available source quality without transcoding. HLS PROGRAM-DATE-TIME is preferred for wall-clock alignment. Fragments without reliable time remain unlocated rather than using download time as broadcast time.

The website origin is locked after account connection and shared by list and anonymous metadata and status requests. HLS defaults to `edge-hls.doppiocdn.net` and then uses the saved manual choice. On a switch, each live producer cancels its old requests and resolves the selected node while retaining its published buffer and recording queue. Manual testing samples up to 2 MiB of real media per node in sequence and uses the result for display and sorting.

Initial and routine sync obtain the signed-in viewer's ID index from `/api/front/users/:id/favorites`. Names come from the batched `/api/front/v2/users` response, avatars from `/api/front/v2/users/profiles`, and default covers from `previewUrlThumbSmall` on `/api/front/models/list`. The status heartbeat uses `snapshotTimestamp` from the same endpoint to version public live covers. Missing snapshots or inconclusive status preserve the current image. Confirmed offline or private status restores the default cover. Missing profile fields preserve saved values. An ID with no saved name uses a temporary label.

For a connected account, sync verifies the account and favorites index, publishes new IDs to the directory, and notifies the workbench before the remaining profile reads finish. Routine heartbeats request names and avatars for new entries and entries still waiting for a name. The full profile refresh runs every five minutes. Batched cards continue to supply covers, status and membership evidence for ambiguous cases. Initial binding and account changes use the existing atomic activation for the account and directory.

The named broadcaster's public room page is the sole source for the disabled-account notice. The exact `/api/front/v2/users/:id` record verifies the ID and current username and supplies `isDeleted` for account deletion. Room pages are fetched anonymously. An archive with no confirmed restriction can return once the signed-in card confirms following, the exact account exists, and the room page check is conclusive. Identity checks rotate in bounded batches.

A confirmed unfollow requires explicit `isInFavorites=false` from the signed-in model card, a positive control in the same response, absence from the valid favorites index, an exact account record that confirms it still exists, and an accessible room page matching the current username. Inconclusive reads preserve membership. Recorded unfollowed and blocked rows remain archived with their reason. Eligible rows without recordings are hidden during cleanup. A fresh disabled-account notice queues an automatic unfollow for an empty archive through the same account write queue. Local cleanup starts after the site acknowledges the unfollow. When an exact single target is absent from the valid index, the site's explicit no-favorites-to-delete response also completes the unfollow. Media commits and cleanup are serialized by broadcaster, with fresh generation, footage, and reclamation checks before deletion. Switching or disconnecting the account revokes the previous binding's cleanup eligibility.

A signed-in room response with the exact ID and `isGeoBanned` provides regional access evidence. Sync keeps checking existing restrictions after the favorites list and batch status recover. An explicit `false` from the room response clears the label. On a plain 403, sync can confirm recovery for a broadcaster still in the favorites index with verified signed-in membership and valid batch status when the matching public room page reports `viewCam.playerIsAvailable=true` for the same ID. Inconclusive reads preserve the stored reason. Confirmed region-restricted broadcasters stay in their live-status group when a valid batch status is available. When unavailable, they are archived with a regional restriction label. Regional restrictions preserve the Favorites relationship and local records. Automatic recording pauses while the restriction is confirmed.

Other missing or expired statuses retain the last known group. IDs awaiting a first status appear at the bottom of the offline filter, whose count only includes confirmed offline observations. The directory displays online, offline and archived groups. Online public rooms precede private rooms and each group sorts by current session start, newest first. Offline and archived rows sort by latest recording and then latest online time. New automatic recordings require verified current public status, an enabled policy and writable storage. The recording indicator starts after the first fragment commits. Active playback and capture can recover within the finite evidence lease, and confirmed private status revokes authorization immediately.

## Recording units and UI consistency

Deleting the fragment under the playhead preserves live following in a rolling window. A manually selected window contracts to the surviving footage. If the deletion response is lost, the browser looks up the receipt by command ID. When new history events span several pages, the panel follows the server cursor in order before advancing the read position.

A complete source fragment belongs to one stable recording unit. Units form at roughly minute cadence without cutting video at natural-minute boundaries; a brief interruption does not itself create a new identity. The representative image prefers a decodable frame in the unit's first fragment. Growing units retain their sample anchor and URL. Images, selection snapping, favorites and deletion share the unit identity.

Live time, playback cursor and committed-media end are separate. Clicking an image seeks without freezing the live window; dragging a selection fixes the range. The server produces limited gaps and compressed page cells; clients must not infer page numbers from elapsed minutes. An image not yet generated differs from absent media.

Favorites are durably accepted and logically protect media before batched materialization; later members of an open unit inherit protection. Deletion durably accepts an intent and logically hides media before member preparation and physical reclamation. Acceptance seals selected open units and records the recording revision so subsequent footage stays outside the old task. Select-all uses a frozen selection token plus explicit exceptions, not a complete browser-side library list. Personal revisions and deletion generations reject stale results.

Preparation and reclamation share 64 processing slots. Confirmed overflow jobs are persisted in the same journal with state `waiting`. When a job finishes or startup recovery runs, the archive transaction fills available slots in admission order. Workers keep per-broadcaster ordering and bounded cross-broadcaster concurrency. Resuming waiting jobs requires a version that supports this state.

After the target recording units are frozen, their full time bounds constrain fragment discovery. Each list page, ordinal range, and cursor is written in the database. Reclamation can begin as soon as a page is durable. The archive tombstones fragments in batches and reclaims the objects from that batch. After directory sync, one durable transaction acknowledges the objects and advances the job cursor. Other archive reclamation retries with independent backoff, including with keep-forever retention. Diagnostic logs distinguish queue wait, plan steps, tombstones, file reclamation, directory sync, and progress acknowledgement.

Delete unliked preserves the favorite exclusions in effect at admission. If a favorite is removed while a job is waiting or preparing, the same durable transaction records the matching exclusions in affected deletion intents. The original deletion continues across restarts. The status panel treats a terminal cancellation under the earlier favorite revision guard as historical and reports current issues separately.

UI reads and cancellation are owned by business scopes. SSE signals invalidation, not complete business data. Timeline reads currently use three rows per packet and two packets in flight, with bounded caches prioritizing visible rows. Unchanged subject objects are reused; connection geometry is locally subscribed; animations follow actual geometry changes with batched measurements before writes. Exact playback updates do not redraw the whole coverage band, and archive time mapping uses a cumulative index with binary search.

Native scrolling keeps the full height of the filtered directory and mounts only rows near the viewport. Virtual spacers draw cover placeholders and both rails during large jumps. Nearby offscreen covers preload only from the local cache, with transfer slots reserved for visible rows. Scrolling across rows pauses directory timeline reads and retains already painted detail. Newly exposed rows show their covers and rails during motion, even with cached data. After 120 ms without scrolling, they paint cached detail and load missing data in batches. The calendar grid and live marker span the viewport height. View bounds determine tick geometry, and the display clock moves the live marker. The player's focus timeline updates independently. Restoration and the player connection retain exact offsets.

After scrolling settles, a span changes, the view pages sideways, or the filter changes, the viewport reveals both tracks from top to bottom, including cached rows. During paging, the outer scene follows the shared horizontal pan while the tracks fade in inside it. Requests still run in parallel. A lower row that finishes early waits in the cache for preceding rows to become ready or report an error. A soft sweep indicates pending data and fades out as the tracks fade in. Offscreen and scrolling placeholders stay static, and painted rows stay visible during background refreshes.

The browser cover cache keeps image bytes. Each mounted image creates its own display URL and releases it on unmount, so a returning row can still display the cached bytes. The player and monitor wall use the same broadcaster cover as their waiting background, refresh it with the sync heartbeat, and fit the whole image at its original aspect ratio with a 5px Gaussian blur.

After account connection commits the roster, background workers immediately queue avatars and default covers for all followed broadcasters. Scheduled roster refreshes check for new broadcasters and changed image URLs. An unchanged source with a valid local file reuses that file. Default covers are cached separately from live previews and can be shown when a broadcast ends. Background cover jobs use image URLs supplied by roster and status sync. When there is no URL, jobs wait for new metadata. Failed downloads retain existing images and retry on the shared business clock. One manual retry processes every eligible failed cover in batches under the existing concurrency limit.

The broadcaster list and screenshot area use the same stationary neutral glass rails. Loading and horizontal paging animate the data layer. Status and recording colors follow their respective time intervals, and gaps in recordings show the base rail. Each coverage color uses one SVG with at most 15 density paths, preserving gaps and subpixel markers. Wide views favor whole-minute buckets aggregated in PostgreSQL. Covers and timelines move together, with the selection and player connection following. Timing and easing reuse existing motion tokens; no animation dependency is added.

Online, offline, and archived filters toggle independently. The glass highlight indicates selection, and selected groups appear in that order. Public broadcasters appear before private broadcasters in the online group. Each status is sorted by the start of the current online session, newest first. Offline and archived broadcasters are sorted by most recent recording and then by most recent online activity. ## Concurrency and scheduling

The status panel shows a muted inline notice for the first two consecutive failures of a scheduled sync. The third failure raises an alert in the row and on the toolbar's status button. A successful sync clears the alert. Image refresh tracks consecutive download failures for each image. Scheduled syncs continue automatically, with a separate notice when the account needs updated cookies.

When the first foreground cover lookup discovers an image URL but its download fails temporarily, background retries retain that URL. A new roster source or offline status can supersede it. Retry outcomes reflect the actual download and cache write.

The settings form submits only the fields the operator edited. Before committing each batch of automatic deletions, the archive checks the retention period that authorized the sweep. Saving keep-forever or changing the period stops uncommitted deletions under the old policy. Already committed deletions may finish reclaiming files. Manual deletion uses the range the operator confirmed.

The shared clock schedules empty-date cleanup at service startup, one minute after local midnight, and hourly. The next available resource tick also checks when a confirmed media deletion finishes. The first minute after midnight gives recording fragments time to reach disk. The current day's history is always retained. Each batch rechecks for footage inside the archive transaction, and fragments pending deletion protect the date's history until the archive applies their deletion. Cleanup removes broadcaster status intervals, historical events, stale coverage summaries, and completed runs wholly inside the skipped interval in batches. Status intervals spanning the gap keep their portions on either side. Active runs and runs spanning retained dates remain available. Media files, settings, diagnostic logs and idempotency records follow their own lifecycles. `STV_CLEAN_EMPTY_DAYS=0` stops historical cleanup while leaving timeline compression active.

If the settings or database volume falls below the free-space threshold, both recording and automatic cleanup pause. When they share a disk with media, free space outside the library or expand the volume before retrying the disk check. If only a separate media volume is low, configured retention cleanup can still run.

[execution-policy.ts](../apps/server/src/runtime/execution-policy.ts) plans network, decoder, file IO, publication and database capacity from effective CPU, memory and container constraints. Recording has no fixed room count, but buffers and queues remain bounded. More concurrency does not guarantee proportional HDD throughput.

Media visibility first locates candidate fragments or recording units, then checks indexed membership in accepted deletions. During a unit-based deletion, directory sorting uses the latest remaining visible unit. Live playback, recording supervision, and image jobs only request the subject identity and status they use. Concurrent directory reads share one query, and task summaries use the background read pool. A rolled-back busy write can be retried. An uncertain publication still triggers archive recovery. The status panel groups tasks under Recording, Data Sync, Media Processing, and Archive and Storage. Each task has its own progress, schedule, or diagnostic row. Archive health, disk space, retention, and integrity scans share a group and keep separate diagnostics. A retry runs only the independent recovery action for its item. Bound-site checks validate the expected configuration payload, and archive checks read revision indexes for media, events, and personal data. Image versions that have not changed keep the cached file. Static image transport failures can use the verified mirror, retaining the original content version and reusing a working route. Routine heartbeat and manual site testing remain in diagnostics and the account panel.

The sync pulse reads subject state and the media, event, and personal-data revisions. Views fetch the full directory or unread count when their data changes. Read-only POSTs emit no invalidation. Newly seen evidence notifies the timeline on its own topic. Timeline aggregation reads minute summaries and boundary details in one query. Point lookup and coverage repair use the actual overlap, with a partial index for long fragments. Cleanup marks objects in batches and publishes only the affected recording-unit range.

Initial workbench reads wait up to 250 ms for SSE `ready`. A late connection or reconnection refreshes the active views. The timeline batch reader owns its initial load, and the SSE subscription handles subsequent invalidations. Changes to the configured heartbeat interval keep the stream connected.

The [sync state reader](../apps/server/src/http/sync-state.ts) derives invalidations from media revisions and subject observations. The [SSE transport](../apps/server/src/http/sync.ts) owns connections, ordered delivery and backpressure. The snapshot and focus views subscribe to the selected subject. The directory batch reader retains its usable data and refreshes the affected rows. A cached offscreen row refreshes when it returns. A broad invalidation takes precedence when messages coalesce.

The [timeline data hooks](../apps/ui/src/features/timeline/use-track-data.ts) own read scopes, invalidation and lifetime for the directory and focus view. Rendering paints both projections against coverage, so a subpixel gap stays empty and a growing tail preserves the viewed prefix. It can recover through the dedicated endpoint when the inventory is unavailable.

Database pools separate general reads, playback, background reads, snapshots and writes. Foreground batches alternate fairly with bounded background steps. Recording-unit backfill is background work. The single journal writer guarantees ordered logs and fsync consistency. Interactive and playback read-only transactions limit each SQL statement to 15 seconds. Connection-pool wait is timed separately. Connections are discarded when rollback fails.

A workbench disconnect stops new rows and releases the coverage request's wait on the shared recording-unit index. Workbench coverage and status history propagate cancellation through the read-only RPC. A pending pool lease is returned when granted. An issued SQL statement settles before its transaction rolls back and releases the slot. Pool wait, in-flight SQL and rollback contribute to request drain time.

The status panel groups sync, covers, recording, screenshots, deletion, favorite materialization, retention, integrity and checkpoints. ## Storage and recovery

The hot index records whether it successfully restored the initial checkpoint. An interrupted restore can retry against the same index even if the checkpoint sequence is zero. Completed and failed deletion commands retain a compact receipt when they age out of the recent task list, so retries can recover their original result. Receipts already lost before an upgrade can only be reconstructed if replayable history survives.

`data` contains deployment credentials, logs, and the PostgreSQL cluster. PostgreSQL stores hot indexes and private settings. `media` is the portable library. The database directory uses a local filesystem. Only one instance may write a media library.

```text
data/
  private/                        Configuration master key and database credentials
  logs/                           Rotated logs
  backups/                        Frozen copies when upgrading legacy databases
  postgres/18/                    PostgreSQL cluster
media/
  library.json                    Library identity and checkpoint references
  catalog/                        Current and previous NDJSON checkpoints
  postgres-journal/               Ordered commit logs
  subjects/stripchat-<ID>/
    images/                       Default cover, current cover and avatar
    recordings/YYYY-MM-DD/HH/     Original fragments, bucketed by UTC date/hour
    recordings/unlocated/         Media without reliable wall-clock location
    recordings/.staging/          Unpublished writes
    thumbnails/YYYY-MM-DD/HH/     JPEGs and source-validation metadata
```

The broadcaster key is `stripchat:<ID>`; names and automatically recorded former names are metadata. Paths are relative to the library root. Day/hour directories bound directory size, while requests use database indexes instead of rescanning video files. PIN, cookies, address keys and private network configuration are excluded from media checkpoints.

Media is written temporarily, fsynced and atomically published. Actual database row changes are fsynced to the media journal before committing hot indexes and acknowledging callers. Checkpoints pin a consistent snapshot and stream it without loading the whole database into memory. Current/previous checkpoints and required logs are retained. Missing indexes are rebuilt from them. Invalid complete records or sequence gaps cause explicit failure rather than silently discarding corruption.

Screenshots are recoverable background work. The background worker reuses valid JPEGs after checking both the image and its source. Deletion works in bounded batches, ordered within each broadcaster. If a deletion batch encounters a busy read while preparing its journal entry, the same job retries and the archive stays available. An uncertain journal write enters archive recovery. File reclamation can retry independently after a committed tombstone.
